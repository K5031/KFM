# Decisions

Small choices the design notes leave open.

## Fleet

| Choice | Decision |
|---|---|
| Ids | `u1`, `u2`, ... in the order units are added; the lead is `u1` |
| States | planned (in the fleet and not begun: it begins when the fleet runs and it has a task), starting, working (between check-ins included), waiting (asked its supervisor), done (reported), idle (stopped without a report), failed, stopped |
| Defaults | top rank 5, 12 units, $10 for the fleet, $2 per unit, check-ins every 5 to 300 seconds |
| What agents are told | Facts and what each tool does, and nothing on how to work: who the agent is, its task, who is above it, what `finish`, `ask`, `delegate`, `message`, `status` and `report` do, that every agent shares one folder and nothing keeps two from changing a file. The brief, the notices (resumed, model or task changed, an agent added or removed, the person spoke to an agent), what a supervisor gets when an agent asks, fails or stops, the fleet tools' descriptions and the fleet's refusals are all written that way (`units.py`, `manager.py`, `tools.py`, `fleet.py`). Instructions were taken out on 2026-11-14 at the user's word: they cap what a capable model does by itself, have side effects, and go stale. One of them, telling every rank above K1 that organising is its work, was what had made a lead build a team in that day's runs; without it a lead may work alone again, which is then its judgment. `tests/test_units.py` fails on instruction wording in a brief |
| Names | An agent has no name unless the person, or the agent that hires it, gives one (the `delegate` tool's `name` is optional); the lead a task starts has none. A nameless agent is its rank on the chart and in the agents list ("K4"), rank and id where agents must be told apart (`Unit.called`: "K4 u2", in the timeline, dialogs, the CLI and as the name its harness is given), and "K4 agent u2" in what agents read (`Unit.label`). Its brief says "You are a K4 agent" |
| Team | Inherited from the supervisor unless `delegate` names one |
| A finished unit | Its process is closed; a message to it starts it again on its conversation. Its goal has ended, so it is given its instruction again (`Session.instruct`) and ends it the ordinary way, with a report. The message is sent first and the instruction after it: Kadence starts a turn by itself for a goal set on a resting conversation, on the words "New goal" alone, before the message is there to read; sent this way the turn is the message's, and the goal is set while it starts (`tests/test_manager.py` finishes in that turn on a real Kadence unit); a first request to the model made before the goal is there leaves it for the next. An agent that answers and does not finish has made no report: its goal stands, and where its program lets it go, it shows as stopped without a report. A `finish_goal` call from a unit without a goal is not a report (Kadence refuses it) |
| A supervisor that has finished | Still gets its agents' reports, which start it again |
| Fleet tool permission | Granted by the manager for the conversation (`allow_conversation`), once per tool |
| Tool caller | A token per unit in the server's URL (`?unit=`), compared in constant time |
| Fleet folder | `~/.kfm/projects/<project>/fleets/<date-time>/`: every fleet is in a project; settings in `~/.kfm/fleet.toml` |
| Service | `kfm serve`: a Unix socket `~/.kfm/service.sock` (mode 600), one JSON object a line, first line `{"kfm": 3, "pid": ...}` (the contract's version, raised whenever what goes over the socket changes). A frontend that meets a service of another version is refused at once, with a message that says the service ends by itself when it has nothing to do and names the command that ends it otherwise (`kill <pid>`, the pid from the first line). A request is `{"id", "method", "args", "kwargs"}`; what happens comes as `{"update": "happened" \| "updated" \| "listed", ...}`. A frontend that finds no service starts one detached, its output in `~/.kfm/service.log`, and waits up to 15 s. The service ends 5 s after the last fleet stopped and the last frontend left. Every update goes to every frontend. An event names units by their ids. The manager says when a fleet's record or state changed, at the change and before any event that tells of it (`Manager._changed`), and the record is sent then: a frontend's record has the units an event names, and spending arrives as any other change does |
| Ids | A project's id is its folder's name, a fleet's `<project>/<folder name>`; both are checked to be plain names before they become paths |
| A page's history | An event's number is its line in the fleet's log. `history` answers with the events and the number of the last one it covers, and each `Happened` carries its number: a page shows the history and then every event with a higher number, holding those that arrive while the history is fetched. The service writes the fleet's log out before it reads it |
| `kfm run` | Its fleet goes into the project whose work folder is the one it runs in (made, named after the folder, if there is none) and is called "fleet N" unless named. It is stopped when its task is done or on Ctrl+C, as before the service; `--detach` leaves it running. `--config`, `--fleet`, `--unit-budget` and `--top-rank` are gone: those are settings (`kfm settings`, `fleet.toml`) |
| Fleet record | `fleet.json`, format 8: the units (each with `session`, what its harness opens it on again), `work`, `settings` and `manager_pid`; written on every change of a unit's state or spending, and when the manager starts and stops |
| Resume | Units in starting, working or waiting are started again, in the order they were added; a unit that never got its task is planned again and begins; each of the others is given its instruction as the record then has it and sent `units.RESUMED` |
| Spending limit | A fleet that reaches it stops, as if stopped by the person, and says so in its feed; it is tested where a fleet starts, so one at its limit starts only with a higher one |
| Harness | `harness = "kadence"` by default; its options: `config`, the Kadence configuration every unit starts from (default `~/.kadence/config.toml`, taken without its `[frontend]`; the unit's model, permissions and budget are set under `[runtime]`), and `command`, how Kadence is started (default: KFM's own Python with `-m kadence`) |

## Fleet window

Design: [Agent Note](notes/implemented/2026-11-12-fleet-window.md).

| Choice | Decision |
|---|---|
| Record | `log.jsonl` in the fleet's folder: one JSON object per event, `t` (seconds), `type` (the event's class) and its fields, units by id as in the event itself; written in batches off the event loop, in order; a line that cannot be read is left out |
| Timeline | Lines only for states nothing else shows (failed, stopped, idle); starting, working, waiting and done are in the agents list. A report, question, update or failure is a card (the theme's `card` colour); one addressed to the person has an accent outline. In a fleet that does not run, the agents list shows working and waiting muted. Entries are one column of at most 720 px in the middle; what an agent wrote stands under its name, in line with a card's text. In the agents list the name takes the spare room and the chosen row is rounded like a project's |
| An agent's task | "Task…" in an agent's menu. The agent's standing instruction is replaced in the conversation it has (`Session.instruct`, for Kadence its `set_duty`): a message alone would leave the old task in what it reads at every check-in. It is then told to leave the old task, and its supervisor, if at work, what the new one is. One that has not begun begins on it. In a stopped fleet the task is kept in the record and the agent is opened on it when the fleet starts: it is then told the fleet was started again, and reads the task in its instruction |
| Removing an agent | "Remove…" in an agent's menu, after a question that says how many agents go with it. The agent and everything under it stop and leave the record; their folders under `units/` are deleted, and what in the timeline names them goes too: `history` leaves it out, and a page drops it when the record no longer has the agent, in every frontend. The supervisor, if at work, is told the work is not being done. A number is never given twice: `fleet.json` keeps the next one, so a removed agent's id is not reused after a restart. What the removed agents spent stays in the fleet's total (`removed_usd`, format 7): otherwise removing agents would make room under the spending limit |
| Failures in the manager's own work | Saving, passing a message on and closing a unit run as tasks nobody awaits. One that ends with an exception is logged with its traceback and shown as a notice in the fleet's feed, so that it is not lost. A record (`fleet.json`) or a log line that cannot be written is one of them; a change the person asked for is refused with the error instead. A log that cannot be written says so once and is not tried again until the fleet's manager is closed |
| Renaming | "Rename…" in the right-click menu of an agent's box, a fleet's name and a project's row; one line, and an empty name changes nothing. An agent or fleet is renamed while it runs or not (`Manager.rename`, or the record). No agent is told: they address each other by id, a message would wake an agent that has finished and cost a turn, and what reaches a supervisor afterwards carries the new name. The renamed agent's own brief still has its first name. Earlier entries of the timeline keep the name of their time |
| Deleting a fleet | Right-click on its name on the chart, "Delete…", the same dialog as for a project. The fleet is stopped, then its folder is removed (`fleet.delete`, which refuses a folder with no `fleet.json`); the work folder stays |
| Deleting a project | Right-click on its row, "Delete…", then a dialog that says what goes and what stays, with Cancel as the default. Its fleets are stopped, then `<home>/projects/<when>/` is removed (`project.delete`, which refuses a folder with no `project.json`). The work folder is never touched: it is the user's, and may hold what they had before |
| An agent's page | The fleet page with one agent chosen is that agent's conversation, laid out like a Kadence chat: the person's words in bubbles on the right (the task they gave is the first), the agent's writing on the left without its name on every entry, and what others said to it (its supervisor's task and messages, its agents' reports and questions) as cards that name the speaker. The bar shows "fleet › agent" and the agent's state and spending. It is not made to look private or turn-based: hiding the other speakers would show an agent reacting to nothing. What goes down the chain is an event of its own (`Instructed`: a task or a supervisor's message), kept in the log; the whole fleet's feed shows it too |
| Files with a message | The fleet's message box is Kadence's: the strip of attached files (`AttachmentStrip`), "Add files", and files dropped or pasted into the text. The unit contract carries them (`Session.send(text, files, spoken=)`, which Kadence's own `send` already takes), so a second harness decides what it does with a file. A message that is a taskless agent's task is followed by its files as a message of their own; with files and no words it is refused, since a task cannot be empty. A supervisor told of the person's message to its agent is told the files' names |
| Profile corner | The sidebar's bottom is Kadence's: the user's name with a round letter (the system's user name, `theme.avatar`) opening a menu (Settings, Add to App Menu while the app menu lacks it, Quit), and a gear that opens Settings. Kadence's `profile` and `gear` styles are used as they are |
| Settings | A dialog over `<home>/fleet.toml`: a model id for each rank (empty: the agent program's own), what a fleet and an agent may spend, the most agents in a fleet. `config.save` writes them beside whatever else the file says and refuses what does not fit, so nothing is half written. They are the defaults of new fleets: a fleet's own record keeps what it was made with. Teams' models, permissions, the agent program and the check-in times stay in the file only |
| Message to one agent | The box sends to the agent chosen in the agents list, and says so; otherwise to the lead (`Service.say(fleet, text, unit)`). Relaying through the lead rewords a correction at every rank and costs each a turn, and a person who can place an agent should be able to speak to it. To keep one chain of command the agent is told the message is the person's and stands over its supervisor's word, and the supervisor is told what was said, unless it has ended: it is not woken for it. It is the exception: nothing targets a worker unless one is chosen |
| Message to a stopped fleet | Sending one starts the fleet again and then delivers it, so a lead's question can be answered without pressing Resume first. The box is off only while the fleet is stopping or it has no lead; a message sent while it stops waits for that and then starts it. If the fleet cannot start, the text is put back in the box |
| Agents | A tree by supervisor: name and rank, state (accent while at work, warning while waiting, green when done, red when failed), spending; refreshed every second while the fleet runs |
| Status | running, stopping (until its processes have ended), stopped, not started (no agent has begun), or finished (the lead has reported and nothing is at work) with what was spent of the limit. The service works it out (`FleetState.status`), with whether the fleet can be started and whether it has run; the window and `kfm status` show what it says. The colour of an agent's state is one function for the chart and the agents list (`chart.state_tone`) |
| New fleet screen | The logo, a heading that names the project ("New fleet in Acme"), the fleet's name ("Fleet name", where the project's screen says "Project name": the two screens look alike and a project's name was taken for the fleet's), one box for what it does (Kadence's `MessageBox`: Enter starts, Shift+Enter a new line) and along its lower edge Task or Duty (Duty by default: a fleet in a project holds a role), the folder, the limit ("Up to $", 10 unless the settings say otherwise) and the start button; a few words under it say what the chosen kind means. With nothing in the box the fleet is made with no agents, for the person to build (the placeholder says so: "What it does, to have a lead build it (optional)", as the project's box says of its own). It is reached with Add fleet on the chart, also in a project with no fleet: a new project opens on its chart, so the person sees the project before being asked for a fleet. No text explains the product |
| Work folder | Chosen by the person for each project: none is suggested or remembered, and KFM makes none (a default `~/kfm-work` was built first and was a folder nobody asked for). A project without one, with one that does not exist, or with the home folder is refused with a line under the box. A new fleet has its project's folder unless another is chosen |
| New fleet | In `<project>/fleets/<date-time>/` (with `-2`, `-3` when that exists), with the settings of `<home>/fleet.toml` and the limit from its screen |
| Projects | `<home>/projects/<date-time>/project.json` (`format` 1: name, work folder). Listed in the sidebar, newest first, drawn by Kadence's `RowDelegate` with the number of fleets and how many run; the window opens on the newest. Fleets of a project left open keep running |
| Draft | A new project's box takes what it should do; left empty, the project is filled by hand. The drafting agent is unit `u1` "Planner" at the top rank, in `<project>/planner/`, with the settings' model for that rank, their permissions and one agent's limit; its tool server has the one tool `propose(teams)`, each team a name, what it does and `ongoing` (true unless said), and refuses an empty list and a repeated name. The draft page's limit is for each fleet. Start is refused while a fleet lacks a name or what it does, or two share a name |
| Chart | A fleet's tree by `chart.slots`: an agent with nobody under it takes a column, a supervisor stands over the middle of its agents, the row is the rank's distance from the top. Agents are 168 x 56 px boxes joined by elbow lines. Each fleet is a card (the theme's `card` colour, 14 px corners, at least 250 px across inside) with its name, its state and Start or Resume at the top and its tree in the middle; cards stand 20 px apart in the order the fleets were made, in the middle of the screen, and go on to the next line when the window is too narrow, so the chart never scrolls sideways unless one fleet is wider than the window. Cards on a line are as tall as the deepest tree on it. "Add fleet" is a dashed place of a card's height after the last. While a fleet does not run, what its agents were doing (working, waiting) is shown muted; done and failed keep their colour. Redrawn every second, on every event and when the window is resized, keeping the boxes |
| Agent menu | Right-click on a chart box: "Add agent…" (not for a K1) and "Model…", in a running fleet and a stopped one (not while it is stopping). A fleet with no agent shows a dashed "Add agent" box where its lead goes. A fleet that can be started shows Start beside its name; a start that fails opens the fleet, where the reason is written. An agent that has not begun has the state `planned`. Add agent is a dialog with name (may be empty, so that nobody has to decide a role before the work is known), task (may be empty), Task or Duty (Task unless chosen), and model; what the fleet refuses is shown in it and it stays open. An agent's own model is in its box's tooltip. Each unit's `model` is in `fleet.json` |
| Bar | 48 px. On the chart: the project's name, how many fleets run and what the project has spent. In a fleet: an arrow back to the chart, the fleet's name, its status, Stop or Resume |
| Column | One column of at most 860 px in the middle of the window; the message box below it is as wide |
| App menu | `app_menu.py`, as Kadence's: `io.github.k5031.kfm.desktop` and the icon (the user's logo, 512 x 512 with clear corners and the same margin around its tile as Kadence's icon, in `hicolor/512x512/apps`) under the user's XDG data directory; the entry runs this install's Python with `-m kfm.desktop`; the icon's file name carries a hash of its content |

## What agents are told

The user's rule (2026-11-12): nothing is hardcoded for a case; it is brittle and does not
generalize.

| Choice | Decision |
|---|---|
| Order | What an agent should do is reached for in this order: the model's own judgment; structure, so the right behaviour falls out of how the fleet works; one general principle, stated once; never a rule for a specific case or a patch for one observed mistake |
| The brief | Situation only, the same for any kind of fleet: who the agent is and its rank, its task, who gave it and that nobody watches, how to finish and how to ask, whether it can hand work down, that everyone shares one folder. What a unit is told when the fleet resumes is a fact it cannot know otherwise |
| Not added | "Report where the results are, do not paste them" and "pass on what you know": the lead did the second unasked, and the first cost cents in runs of two minutes. Nothing is added on a hunch |
| Known soft spot | "Say in each task which files it owns" stands in for a mechanism that is missing: nothing stops two agents editing one file |
