# Agent Note: Build

Status: proposed — a third kind of fleet beside Task and Duty: the lead can read but not write or hire until the person has approved its plan, and then builds it with the agents it chooses

Related: [a project's secretary](../implemented/2026-11-19-a-projects-secretary.md), whose
proposal of teams is the same step one level up; [standing teams](2026-11-12-standing-teams.md);
[short-lived workers](2026-11-14-short-lived-workers.md);
[shared team memory](2026-11-12-shared-team-memory.md).

## Problem

A fleet is a Task or a Duty, and neither fits work that is large and not yet specified.

- **A task** suits what is small or precisely described. Given something open ("add
  what KFM needs next"), the lead decides what to build and builds it.
- **A duty** is hands-off by design. It can spend on work nobody wanted and get it
  wrong, and the person finds out afterwards.

In the run of 2026-11-14 a lead chose two features by itself, three workers spent $3.03
in nine minutes building them, one crashed on every real use, and the person had both
taken out. A page describing them would have cost cents and been refused before
anything was built.

What is missing is the middle: the person decides what is built and what it may cost,
once, and is then left alone while many agents do it quickly.

## Proposal

A fleet has one of three kinds, chosen where Task and Duty are chosen today (the
person, 2026-11-18):

| | For | The person's part |
|---|---|---|
| Task | small or precisely specified work | says what to do |
| Duty | a role kept going, hands off | stops it when it goes wrong |
| Build | large work done fast by many agents | approves the plan, then is left alone |

A Build is a task with one gate in it. KFM is not an agent and does nothing with the
plan: it does not read it, hire for it or check work against it (the person,
2026-11-18). It carries the plan to the person and the answer back, and holds what the
lead is able to do, as it holds the spending limit.

### Before the plan is approved

- The lead reads and searches the work folder and writes nothing: its permissions are
  read-only, and what it asks approval for is refused.
- It cannot hire: `delegate` is refused with the fact that the person has not approved
  a plan yet.
- It has one more fleet tool, `plan`, which takes the plan as text in the lead's own
  words and shape. The fleet's status is then "plan to approve".

### The person's decision

The plan is shown as the lead wrote it, with **Approve** and a box for a note. A note
goes to the lead as a message, and the lead answers with another plan. In the terminal
`kfm plan` shows it, and `kfm plan approve` or a message answers it.

### After

The lead has a task's permissions and tools. It hires with `delegate` as any lead does,
and gives each agent the limit it chooses (`budget_usd`, which `delegate` takes today).
The fleet's limit stops the whole of it, and the fleet ends when the lead reports.

`plan` stays: a lead that wants to change course can put a new plan to the person, and
the answer reaches it as a message. Nothing closes again while it waits.

**What holds a Build to its plan** is the lead, which said what it would do to the
person who is watching, and the fleet's limit. Nothing in KFM compares the work with
the plan.

## Alternatives considered

- **A plan with parts KFM acts on**: a part's name, rank, limit and what done means,
  as arguments KFM checks; on approval KFM starts one agent for each part, refuses
  `delegate` and holds each part to its limit. Written first. It makes KFM a manager
  that hires and enforces a structure it was handed, which is an agent's work done by
  fixed code: every case the code did not foresee (parts in order, a part split in two)
  needs more of it.
- **KFM running the project's tests when a part reports.** KFM would have to know what
  the tests of every project are. The agents run them.
- **Telling leads to plan and ask before building.** A rule, applied also where it makes
  no sense (a typo, a support team), and one a lead can follow badly. See
  [short-lived workers](2026-11-14-short-lived-workers.md) on rules for agents.
- **Kadence's `propose` tool**, with which an agent puts one action of its own to the
  user. It asks about each action; a Build asks once about all of them.
- **A fleet that only proposes**, with the building done by a second fleet the person
  starts. The lead that read the project and wrote the plan would be thrown away, and
  the second fleet's lead would start cold.

## Acceptance criteria

- Started on open-ended work, a Build spends only the lead's reading before the person
  has approved anything, changes no file and has no agent but the lead.
- A note in place of an approval reaches the lead, and a second plan reaches the person.
- After approval the lead hires and writes as a task's lead does.
- The same open-ended instruction given to a Build and to a Task: measured in what was
  built that the person then keeps.

## Risks

- **A plan can read well and build badly.** It prevents unwanted work, not wrong work.
  Each part's agent runs the project's tests, and checking the parts together is left
  to the lead, which is weakest exactly when many parts report at once.
- **Every agent starts cold.** Ten agents read the project ten times. What the lead
  writes into each task helps; [shared team memory](2026-11-12-shared-team-memory.md)
  is the real answer and is not built.
- **Nothing binds the fleet after approval.** A lead can plan one thing and build
  another, and only the person reading the feed would know.
- **One more place a fleet waits for the person.** That is the point of it, and a Build
  nobody looks at does nothing.
