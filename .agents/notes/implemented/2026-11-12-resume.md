# Agent Note: Resuming a fleet

Status: implemented — `kfm resume` starts a stopped fleet again: every agent that was at work carries on with its conversation, plan and role

Part of [Standing teams](../proposed/2026-11-12-standing-teams.md).

## Problem

A fleet lived as long as its `kfm run`. Closing the terminal, a reboot or Ctrl+C ended
it for good: a team that holds a role for a week cannot depend on one process never
stopping.

Everything an agent needs to carry on is on disk. Each unit is a Kadence with its own data
folder, which keeps its conversation, its duty and its plan. What was lost is the fleet
around them: who was at work, where the fleet worked, and with which settings.

## Decision

- **The fleet's record holds what a restart needs** (`fleet.json`): beside the
  units, the folder the fleet works in, the settings it runs with (`config.record`), and
  the process that runs it now.
- **Stopping leaves the record as it is.** A unit that was working when the fleet stopped
  stays "working" in the record, also when the fleet stopped at its spending limit;
  `kfm status` says whether the fleet is running or stopped. A unit its supervisor
  stopped stays "stopped". Units run in a session of their own, so Ctrl+C in the terminal
  reaches the manager, which closes them.
- **`kfm resume [--fleet PATH]`** (default: the newest fleet) starts a manager on that
  record (`Manager.resumed`) and every unit that was at work (starting, working, waiting)
  on its own conversation. Finished units stay closed until a message starts them, as in
  a running fleet. `--budget` and `--unit-budget` replace the saved limits, which is how
  a fleet that stopped at its limit goes on; without more, such a fleet is refused.
- **A resumed unit is told what happened** (`units.RESUMED`): the fleet was stopped,
  whatever ran in the background is gone, look at what changed, ask again if an answer
  never came. A Kadence that opens a conversation with a duty waits for a message before
  it schedules anything, so this message is also what sets the unit going.
- **Units get the fleet tools at their new address**: the manager writes a unit's Kadence
  settings each time it starts the unit's process.
- A fleet whose manager process still exists is not resumed a second time.

## Alternatives considered

- **Keep the manager running for good** (a service). A fleet would still end with a
  reboot or a crash, and resuming is needed to recover from both; a service can be built
  on it later.
- **Mark every unit stopped when the fleet stops.** Built first. Nothing then tells a
  unit its supervisor stopped from one the shutdown interrupted.
- **Reopen the units and let their duties' schedules run.** Built first, on the wrong
  reading of Kadence: a reopened duty waits for a message. In a real run the resumed agent
  did nothing for three minutes.

## Consequences

- Checked with Claude Sonnet 5.5: an agent holding a maintenance duty was stopped after
  a minute; a request was put into its inbox while the fleet was down. Resumed, it built
  and tested what was asked within 19 seconds and went back to its check-ins. The record
  carried its spending over ($0.11, then $0.27).
- A question an agent had asked is held by its Kadence in memory only: after a resume the
  unit is working again, and asks again if the answer did not arrive before the stop.
- Tool calls and background work that ran when the fleet stopped are lost; the unit is
  told so.
- A manager that is killed outright leaves its process id in the record; a process that
  no longer exists counts as stopped.
- Every resumed unit spends one request on the restart message, also one that had
  nothing to do.
